# Agent-Ready Repository Patterns

## Repository Guidance Entry

```markdown
## Database migrations

- Run `bin/db-migrate`; direct schema edits are overwritten.
- Verify with `bin/check-schema`.
- Production rollback requires the migration runbook in `docs/database.md`.
```

Include the supported path and verification command, not just a prohibition.

## Command Catalog

```markdown
## Repository commands

| Command | Purpose | Mutates data |
| --- | --- | --- |
| `bin/test` | Run the test suite | No |
| `bin/lint` | Check formatting and static rules | No |
| `bin/setup` | Prepare local dependencies | Development only |
| `bin/deploy staging` | Deploy staging | Yes, approval required |
```

## Root Guidance Skeleton

```markdown
# <Project>

<One paragraph: what the project does and its main entry points.>

## Commands

<Command catalog: see below.>

## Boundaries

- <Module or dependency rule, with the check that enforces it.>
- Generated: `<path>` is generated by `<command>`. Do not edit it directly.

## Testing

<Testing policy: see below.>

## Approval required

- <Destructive, shared-resource, external-write, or deployment actions.>
```

Keep only sections the repository has evidence for.

## Testing and Verification

Use this acceptance-first template only when the user or team adopts it. Replace the commands with the project's own.

```markdown
## Testing

Changes to required behavior need passing acceptance tests. Derive expected outcomes from requirements, not from the implementation. If required acceptance checks cannot run or fail, report the change as blocked. Changes with no behavior change reuse existing checks.

| Behavior | Acceptance boundary | Command |
| --- | --- | --- |
| User-facing flows | System tests through the real interface | `bin/test system` |
| APIs and non-UI workflows | Request or integration tests through the public boundary | `bin/test integration` |
| Pure calculations, parsers, algorithms | Unit tests, only when justified | `bin/test unit` |

- Assert the promised final outcome, such as the amount charged, not only a displayed value or status.
- Add a unit test only for specific cases that are costly at acceptance level, materially faster feedback on logic under development, or deterministic reproduction of a known defect. Coverage is not a reason.
- Do not mock our own forms, controllers, jobs, or services. Substitutes for external systems must state what stays unproven.
- A refactor or rewrite keeps the same acceptance assertions. Change expected outcomes only for an established requirement change.
- Remove implementation-coupled and temporary tests when protection at the right level remains.
- Use focused checks while iterating. Run required acceptance and relevant regression checks before handoff.
```

## Teaching Validation Error

```text
ERROR: src/api/orders.ts imports src/internal/database.ts
Reason: API handlers must use the public data-access boundary.
Fix: import OrderRepository from src/data-access/orders.ts
Guide: docs/architecture/data-access.md
```

## Structural Test Questions

- What boundary is important enough to block a merge?
- Can the check parse structure instead of relying on fragile text matching?
- Does the failure identify the smallest correction?
- Can contributors run the exact check locally?
- Is there a fixture proving the validator catches the prohibited case?

## Guidance Placement

- Root guidance: repository-wide commands and invariants
- Nested guidance: package-specific commands, generated-file rules, and local boundaries
- Reference docs: long rationale, runbooks, and provider details
- Scripts: deterministic checks and transformations

Do not repeat the same rule at every level. The nearest applicable guidance should own the detail.

## Maintenance Review

```text
1. Find guidance whose referenced paths or commands no longer exist.
2. Find duplicated rules with different wording.
3. Confirm each important rule has a check or explicit manual verification.
4. Remove historical commentary that no longer changes behavior.
5. Run links, schema, and structural checks after cleanup.
```
